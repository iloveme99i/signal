> 文档基于本地真实项目 `/Users/belief/Documents/工作/signal`、当前可运行页面与代码实现整理。截图来自真实 Signal 页面，不是重绘稿或概念 Demo。截图中的内容均为明确隔离的“作品集演示数据”，不得被描述为真实用户反馈、真实业务数据或量化成果。

## 1. 产品正式名称与一句话定位

**产品名称：Signal**

**一句话定位：** 一个本地优先的个人信息识别与分类工具，把分散在截图、收藏文字和混合备忘录中的内容轻度整理后放入用户自己的分类体系，并保留原始来源以便查找和核对。

## 2. 产品来自什么真实自用问题

Signal 来自一个持续发生的个人信息过载问题：小红书、抖音、牛客、招聘平台和网页中的收藏不断增加，手机里还积累了大量截图；备忘录和 Notion 中也保存着零散想法、岗位、工具与学习资料。信息被收藏之后往往没有时间重新阅读，长视频的消费成本更高，最终形成“保存很多、真正使用很少”的堆积。

真正需要的不是再做一个收件箱，也不是让 AI 输出冗长分析，而是一条每天愿意使用的短链路：把材料放进来，Signal 理解原意、轻度整理、匹配分类，并保留原文和来源。

## 3. 目标场景和核心问题

### 目标场景

- 批量整理手机截图中的岗位、教程、工具和灵感。
- 将一段混合了多个主题的备忘录整理成少量上下文完整的记录。
- 按自己创建的多级分类树保存信息，而不是被系统预设分类绑住。
- 以后通过分类、搜索、收藏、置顶、最近使用或看板重新找到内容。
- 打开一条记录时同时看到整理后内容、个人备注与原始来源。

### 核心问题

1. **来源碎片化：** 信息分散在多个 App、网站、截图和备忘录中。
2. **整理成本高：** 手动重命名、复制、分类和补充来源的动作链过长。
3. **收藏后失联：** 收藏夹缺少符合个人习惯的结构，内容难以重新利用。
4. **AI 容易过度加工：** 常见 AI 产品会把原文改写成冗长总结，反而增加阅读负担。
5. **来源丢失：** 只保存整理结果会失去核对入口，尤其不适合岗位、时间和链接类信息。

## 4. 当前真实可用能力

以下能力均来自当前代码和可运行页面，而不是未来规划：

### 内容导入与识别

- 粘贴混合备忘录。
- 单张或批量上传截图。
- 支持 PNG、JPEG、WebP、HEIC 和 HEIF。
- 在浏览器中压缩图片，并通过 Tesseract.js 进行中英文 OCR。
- 批量图片识别时复用同一个 OCR worker，显示逐张处理进度。
- OCR 失败或图片无清晰文字时允许进入人工补充流程。

### AI 轻度整理与分类

- 使用 DeepSeek Chat 对 OCR 文本或备忘录进行结构化整理。
- 默认一份材料保留为一条完整记录；仅当存在彼此无关的主题时才拆分。
- 不生成分析过程、行动建议、价值判断和原文中不存在的信息。
- 根据用户现有分类树的完整路径匹配最具体的分类。
- 保存前提供确认界面，可修改标题、正文和目标分类。

### 用户分类体系

- 用户自建分类和子分类，支持多级嵌套。
- 分类树支持展开、折叠、重命名、删除、复制结构、移动和拖拽调整层级。
- 分类可设置 Emoji、线性图标、强调色和收藏状态。
- 点击大分类后，中栏显示子分类条目及当前分类中的内容；点击子分类可在右栏继续编辑说明。
- 分类说明支持块式文本、Toggle 类型和缩进编辑。

### 信息库与内容管理

- 信息库概览、列表和分类看板。
- 最近使用、收藏、置顶、备忘录、待分类和回收站入口。
- 内容搜索、手动排序、按最近添加排序、按标题排序。
- 内容拖拽排序、拖入分类、批量移动和跨分类引用。
- 内容复制、收藏、置顶、移入回收站、恢复和彻底删除。
- 右栏原地编辑标题、整理后正文和个人备注，自动保存在当前浏览器。
- 每条内容保留原始来源名称、原始文本、来源时间；截图来源还保留压缩后的原图。

## 5. 当前真实核心链路

```text
截图 / 混合备忘录
→ 浏览器本地图片压缩与 OCR（截图场景）
→ 将 OCR 文本或备忘录文字发送到项目的 /api/analyze
→ 项目服务转发到 DeepSeek Chat 进行轻度整理与分类匹配
→ 用户在保存前确认标题、正文和分类
→ 内容、分类、原文与图片保存到当前浏览器
→ 通过分类树、搜索、收藏、置顶或看板重新使用
```

## 6. 从复杂信息分发系统到轻量分类工具的关键取舍

早期方向更接近一个复杂的“信息分发与行动系统”：AI 试图把材料拆成时间、待办、知识、资源和行动，并继续生成结论或计划。实践中出现了三个问题：

1. 一条完整材料被机械拆散，原有上下文消失。
2. 页面需要承载过多 AI 字段、状态和解释，形成明显的信息过载。
3. 系统替用户决定“什么值得行动”，偏离了用户真正想解决的整理与查找问题。

当前版本做了明确收缩：

- **从“AI 替用户判断”改为“AI 帮用户整理”。**
- **从系统预设的时间/待办分类改为用户自己维护的分类树。**
- **从大量仪表盘、结论卡片改为三栏工具界面。**
- **从一句话机械拆字段改为默认保留上下文完整的一条记录。**
- **从追求自动化程度改为强调确认、可编辑和来源溯源。**

这一取舍使 Signal 的核心价值更加聚焦：降低整理成本，同时保留用户对信息结构和最终内容的控制权。

## 8. 作品集演示数据与隐私说明

### 演示数据

- 截图中的岗位、学习、工具和项目灵感均为虚构的非隐私演示内容。
- 数据来源在界面中明确命名为“作品集演示数据｜混合备忘录”。
- 为填充分类列表而增加的岗位条目仅存在于 `signal.localhost` 的隔离浏览器存储空间。
- 演示条目不得写成真实用户收藏、真实招聘结果、用户反馈或业务增长数据。

### 数据保存边界

- Signal 当前是本地优先、单人自用工具，不需要登录。
- 内容、分类、图片、来源、收藏和置顶状态主要保存在当前浏览器的 localStorage 中。
- 不同浏览器、不同设备以及 `localhost` 与 `signal.localhost` 之间不会自动同步。
- 图片以压缩后的 Data URL 保存到浏览器，本地存储容量可能成为大量截图场景的限制。

### API Key 与模型调用边界

- DeepSeek API Key 保存在当前浏览器的 `signal-deepseek-key` localStorage 项中，不写入 Git。
- 当前实现并非“所有数据永不离开本地”。
- 进行 AI 整理时，浏览器会把 **API Key、原始文本、标题和可用分类路径** 发送到项目自己的 `/api/analyze` 接口。
- 项目服务再把 API Key 和上述文本发送至 `https://api.deepseek.com/chat/completions`。
- 当前截图 OCR 在浏览器内通过 Tesseract.js 完成；发给 DeepSeek 的是 OCR 后的文本，不是原始图片文件。
- 从当前代码看，项目没有把 API Key 写入数据库、仓库或服务端持久化文件；但请求仍会经过项目服务和 DeepSeek，应按照第三方模型服务的数据政策理解传输风险。

## 9. 尚未完成或未经验证的边界

- 尚未支持小红书、抖音、牛客、BOSS 直聘等平台收藏的自动抓取或账号连接。
- 尚未支持网页链接解析、视频链接解析、音视频转写和长视频内容抽取。
- 尚未提供跨设备同步、云端备份或多人协作。
- 尚未形成手机分享扩展、浏览器扩展或系统级快捷入口。
- 分类块编辑器只实现了当前轻量能力，不等同于完整 Notion 编辑器。
- localStorage 保存 Base64 图片存在容量上限，尚未迁移到 IndexedDB、对象存储或数据库。
- OCR 与 DeepSeek 分类效果尚未建立正式评测集；没有可报告的识别准确率或分类准确率。
- 没有真实用户规模、留存率、节省时间比例、商业结果或外部验证数据。
- README 目前仍是 vinext starter 的通用说明，不是 Signal 的正式产品文档；作品集应以本交接包和真实代码为准。
